# SlayQL Streaming Query and Visualization UX Implementation Plan

## 1. Purpose

This document is the implementation source of truth for the streamed SlayQL query experience and the dedicated visualization module. It supplements the main enterprise demo plan and resolves the details that were previously described only at a high level.

Another implementation agent must treat the requirements in this document as acceptance criteria, not optional design suggestions.

The intended outcome is a demo that:

- Feels responsive during model and database work.
- Shows truthful, inspectable SlayQL progress without exposing private model chain-of-thought.
- Makes it obvious how the question became validated SQL.
- Never presents incomplete or unvalidated SQL as runnable.
- Produces useful charts only when the returned data supports them.
- Supports a maximum of five simultaneous users on the existing VPS.
- Uses the existing third-party model gateway rather than hosting a model.
- Looks like a credible enterprise product even though all queryable data is synthetic.

## 2. Relationship to the main plan

Implement this document together with `SLAYQL_DEMO_IMPLEMENTATION_PLAN.md`.

Where this document is more specific about streaming, query states, results, visualization, or related testing, this document takes precedence.

This work does not require:

- AWS or another cloud compute instance.
- Kafka, Redis, a message broker, or a distributed event bus.
- More than one backend worker.
- GPU capacity.
- A separately hosted language model.
- Large-scale dashboard concurrency.

## 3. Current repository assessment

The repository already contains the visual beginnings of both experiences:

- `src/mock/mockData.js` defines simulated `SSE_STEPS`.
- `src/views/DashboardView.jsx` advances a local query state machine.
- `src/components/ChatWorkspace.jsx` and `src/components/EngineWorkspace.jsx` simulate progress with timers.
- `src/components/dashboard/ReasoningTrace.jsx` displays a mock explanation.
- `src/components/dashboard/SqlResultPanel.jsx` uses Recharts for basic bar, line, and pie output.
- Several older components draw charts manually with SVG.
- `src/lib/api/query.js` returns mocked SQL and execution results.

These are presentation prototypes. They do not currently provide:

- A real server event stream.
- A stable event schema.
- Event replay or reconnection.
- Real cancellation.
- Provider event normalization.
- A reliable distinction between model generation and SQL validation.
- Partial, failed, delayed, or disconnected states.
- Deterministic chart recommendation.
- A reusable visualization specification.
- Saved visualizations or dashboard composition.
- Accessible chart alternatives.

The implementation must preserve the strongest existing visual language while replacing timer-driven behavior and one-off chart code.

## 4. Core experience principles

### 4.1 Perceived speed

Give useful feedback within 300 milliseconds of submission. Do not wait for the first provider token before updating the interface.

Immediately show:

- The submitted question in the conversation.
- The selected connection and model.
- A cancel action.
- An active SlayQL trace.
- The first local stage, such as question normalization or schema retrieval.

### 4.2 Truthfulness

Every visible status must be produced from an actual backend state transition. Do not animate through canned stages or invented percentages.

Use determinate progress only for work with a known count, such as catalog candidates checked or result rows received. Use an indeterminate activity indicator for model generation and database execution.

### 4.3 Progressive disclosure

The default view should answer three questions:

1. What is SlayQL doing now?
2. What has already been verified?
3. What can the user do next?

Detailed evidence, timings, schema paths, SQL diffs, and lineage belong in expandable areas. The default workspace must remain calm and scannable.

### 4.4 Interruptibility

Users must be able to cancel a run, answer a clarification, switch models after a failure, edit generated SQL, or return to another page without corrupting run state.

### 4.5 No private chain-of-thought

Do not expose, persist, log, or replay private model chain-of-thought.

The user-facing trace is generated by SlayQL from factual system events, for example:

- "Matched 8 columns across 4 tables."
- "Expanded the relationship path from customers to payments."
- "Verified every SQL identifier against the catalog."
- "Applied the 200-row demo limit."

Do not display:

- Raw provider thinking tokens.
- Provider `reasoning_content`.
- Hidden prompts.
- Provider signatures or encrypted reasoning items.
- Text described as the model's internal thoughts.

Name the UI tab "SlayQL trace" or "How this query was built", not "Chain of thought".

## 5. End-to-end query journey

### 5.1 Idle composer

The composer must include:

- Multiline natural-language input.
- Selected data connection.
- Selected model.
- Schema/table/column mention support.
- Suggested questions based on the selected connection.
- A visible submit icon button.
- Keyboard submission with Ctrl+Enter or Command+Enter.
- Draft persistence per conversation.
- A new-conversation action.

Disable submission only when:

- The question is empty.
- No usable connection is selected.
- The demo run quota is exhausted.
- The current user already has an active run.

Explain the reason next to the disabled control.

### 5.2 Submit acknowledgement

On submission:

1. Add the user's message locally with a pending marker.
2. POST the run request.
3. Replace the pending marker with the server-issued run ID.
4. Open the event stream returned by the server.
5. Move keyboard focus to a single polite live-status region.

If run creation fails, keep the question in the composer and show a retry action. Never discard the draft.

### 5.3 Local preparation

Show factual SlayQL stages as they occur:

- Question accepted.
- Intent and requested measures identified.
- Candidate schema assets retrieved.
- Relationship graph expanded.
- Relevant value hints grounded.
- Provider context assembled.

The expanded evidence for these stages may show:

- Candidate tables and columns.
- Selected relationships.
- Join path.
- Matched business terms.
- Count of schema assets considered.
- Reason a candidate was excluded.

Do not show raw customer values beyond the synthetic demo values already visible to the user.

### 5.4 Clarification

When the question has a material ambiguity:

- Pause the run in `awaiting_clarification`.
- Show one concise question.
- Prefer two to four selectable answers.
- Allow a free-text answer when needed.
- Retain the original question, selected connection, model, and completed trace.
- Show why clarification is needed using factual ambiguity, such as two possible date fields.
- Resume the same run after the answer.
- Allow cancellation while waiting.

Do not silently guess when the choice would materially alter rows, aggregation, date range, currency, or business definition.

### 5.5 Model generation

While the provider is working:

- Mark "Generating a SQL candidate" as active.
- Show provider and model identity.
- Show elapsed time.
- Show "Provider connected" only after the provider acknowledges the request.
- Show a subtle first-token state when the first delta arrives.
- Keep SQL controls disabled.
- Allow cancellation.

Do not render raw partial structured JSON.

Do not make partially generated SQL look valid. The backend must buffer provider output until the provider response is complete and the structured response can be decoded.

If a polished streaming effect is required, show a neutral activity sentence that changes only from real lifecycle events. Do not stream fake SQL characters.

### 5.6 SQL candidate reveal

Reveal SQL only after all of these are true:

1. Provider output is complete.
2. The structured response is decoded.
3. A single SQL candidate is extracted.
4. The candidate parses in the selected database dialect.

Reveal the complete candidate in the SQL editor with a "Validating" status. It is not runnable yet.

Then progressively add actual validation results:

- Statement type accepted.
- Referenced tables found.
- Referenced columns found.
- Join relationships verified.
- Parameter values safely bound.
- Read-only policy passed.
- Demo row limit applied.
- Query plan or dry-run check passed where supported.

Only after all required checks pass should the primary action change to "Run query".

### 5.7 Repair

Allow at most one automatic repair for the demo.

When repair starts:

- Keep the rejected candidate available in a collapsed "Previous candidate" section.
- Show the exact validator category, not provider internals.
- Label the active stage "Repairing an invalid SQL candidate".
- Reveal the new candidate only when complete and parsed.
- Present a side-by-side or inline SQL diff.
- Record the repair in the trace and audit event.

If repair fails, stop. Offer:

- Retry with the same model.
- Switch model with explicit confirmation.
- Edit SQL manually.
- Start a new question.

### 5.8 User SQL editing

If the user changes generated SQL:

- Mark it "Edited after generation".
- Invalidate the previous validation result.
- Debounce local parsing for immediate syntax feedback.
- Require backend validation before execution.
- Preserve generated and edited versions for the run audit trail.
- Provide a diff and a revert action.
- Never allow edits that bypass the server policy engine.

### 5.9 Query execution

After the user runs validated SQL:

- Lock the executing SQL version.
- Show execution elapsed time and cancel.
- Stream column metadata first.
- Stream result rows in bounded batches.
- Populate the table incrementally.
- Delay chart recommendation until enough metadata and rows exist.
- Show truncation as soon as the server knows it will occur.
- Stop at the configured row and byte limit.

Never treat a transport disconnect as a database cancellation. Reconnect and reconcile run state first.

### 5.10 Answer and visualization

After execution:

- Present the table immediately.
- Select a chart only if the deterministic recommendation engine accepts the result shape.
- Show a short answer derived from the returned result.
- Stream answer text if a second provider call is used.
- Show row count, execution duration, truncation, provider, model, token use, and estimated cost.
- Make Answer, Table, Visualization, SQL, SlayQL trace, and Lineage available as stable tabs.

The table is the source of truth. A chart is a view of those rows, not a separate answer.

## 6. Query state machine

Implement one reducer-driven frontend state machine. Do not spread independent booleans across components.

Required top-level states:

```text
idle
creating_run
connecting_stream
preparing
awaiting_clarification
generating_candidate
validating_candidate
repairing_candidate
ready_to_execute
executing
building_answer
completed
cancelling
cancelled
failed
reconnecting
```

Rules:

- Only server events may advance server-owned states.
- Duplicate events must be idempotent.
- Events older than the last applied sequence must be ignored.
- A terminal state cannot transition back to an active state.
- Reconnection is an overlay on the last known state, not a reset.
- Page refresh must restore the run from the backend.
- A clarification response resumes the same run.
- SQL edits create a new candidate revision inside the same run.
- Cancellation can be requested from any active state.

The reducer state must keep:

- Run and conversation IDs.
- Last event sequence.
- Stream connection status.
- Current stage.
- Ordered stage records.
- SQL candidate revisions.
- Validation findings.
- Result column metadata.
- Result row batches.
- Answer buffer.
- Visualization recommendation.
- Usage and timing.
- Error or cancellation details.

## 7. SlayQL SSE transport

### 7.1 Request topology

Use two requests:

```text
POST /api/v1/agent-runs
GET  /api/v1/agent-runs/{run_id}/events
```

The POST body creates the run and returns:

- `run_id`.
- `conversation_id`.
- `events_url`.
- Initial run state.

The GET response uses `text/event-stream`.

Use same-origin secure HTTP-only session cookies so native `EventSource` can authenticate without putting a token in the URL. Do not place API keys, bearer tokens, or reusable stream secrets in query parameters.

Use HTTP/2 at Caddy or Nginx. One stream is allowed per active run.

### 7.2 Response headers and proxy behavior

The event endpoint must send:

```text
Content-Type: text/event-stream
Cache-Control: no-cache, no-transform
Connection: keep-alive
X-Accel-Buffering: no
```

Configure the reverse proxy to:

- Disable response buffering for the events route.
- Disable compression if it delays small event flushes.
- Keep the upstream connection open longer than the maximum run timeout.
- Flush each complete event.
- Support HTTP/2 to the browser.

### 7.3 Event envelope

Every SlayQL event must use one versioned envelope:

```json
{
  "schema_version": 1,
  "event_id": "run_123:42",
  "sequence": 42,
  "run_id": "run_123",
  "conversation_id": "conv_123",
  "occurred_at": "2026-08-11T12:00:00.000Z",
  "stage": "sql_validation",
  "type": "sql.validation_check",
  "payload": {}
}
```

SSE frame:

```text
id: run_123:42
event: sql.validation_check
data: {"schema_version":1,"event_id":"run_123:42","sequence":42,...}

```

Requirements:

- Sequence numbers increase monotonically within a run.
- Event IDs are unique and stable.
- Payloads use stable JSON types.
- Timestamps are server timestamps in UTC.
- Payloads contain no credentials or private model reasoning.
- Unknown event types are ignored and logged by the client.
- A schema version mismatch produces a recoverable compatibility error.

### 7.4 Required events

Run lifecycle:

- `run.restored`

### 7.5 Event payload requirements

`stage.evidence` may include:

- Human-readable summary.
- Count.
- Catalog asset IDs.
- Relationship IDs.
- Duration.
- Evidence classification.

It must not include free-form provider reasoning.

`sql.candidate_ready` must include:

- Candidate ID and revision.
- SQL text.
- Dialect.
- Generation source.
- Referenced catalog asset IDs.
- Created timestamp.

`sql.validation_check` must include:

- Stable check code.
- Label.
- Status: pending, passed, warning, or failed.
- Safe user-facing detail.
- Optional SQL location.

`execution.rows` must include:

- Batch index.
- Starting row offset.
- Rows as arrays, not repeated keyed objects.
- A final-batch flag.

Column names and types arrive once in `execution.columns`.

### 7.6 Batching and rendering

- Do not emit one SSE event for every provider token.
- Buffer answer deltas for 40 to 80 milliseconds before emitting.
- Update React output at most once per animation frame.
- Send database rows in batches of 25, up to the 200-row demo cap.
- Keep each event safely below 64 KB.
- Do not store result-row events after the run terminal event.
- Disable chart animation while rows are arriving.
- Animate the final accepted chart once, unless reduced motion is enabled.

### 7.7 Heartbeats

Send an SSE comment or `stream.heartbeat` every 15 seconds while no business event is available.

The UI should:

- Show no visual noise for normal heartbeats.
- Mark the stream delayed after 25 seconds without an event or heartbeat.
- Enter reconnecting after transport failure.
- Preserve all rendered content during reconnect.

### 7.8 Replay and reconnection

Native `EventSource` reconnects automatically and supplies the last event ID. Support that behavior.

Add an `agent_run_events` control-database table containing:

- Run ID.
- Sequence.
- Event type.
- Safe JSON payload.
- Timestamp.

Persist all non-row events for 24 hours. Keep result rows only in process memory during an active run. On a refresh after completion, fetch result metadata and offer "Run again" rather than pretending old rows were persisted.

On reconnection:

1. Read `Last-Event-ID`.
2. Replay persisted events after that sequence.
3. Deduplicate by sequence on the client.
4. Send `stream.replay_complete`.
5. Continue live events if the run is active.
6. Send the terminal event and close if the run has finished.

If replay is no longer available, return the current run snapshot and a `run.restored` event. Clearly state if live result rows cannot be restored.

### 7.9 Cancellation

SSE is server-to-client only. Use:

```text
POST /api/v1/agent-runs/{run_id}/cancel
```

The backend must:

- Mark cancellation requested idempotently.
- Cancel the provider stream where the SDK permits.
- Cancel or interrupt the database query.
- Stop answer generation.
- Emit one terminal `run.cancelled` event.
- Preserve completed trace events and SQL candidate revisions.

The UI must change the button to "Cancelling" immediately, but only show "Cancelled" after the server event.

## 8. Provider streaming normalization

Do not forward vendor events directly to the browser. Implement adapters that convert every provider into the SlayQL event model.

### 8.1 Normalized internal provider events

Backend-only provider events:

- Request accepted.
- Connection opened.
- Output delta received.
- Structured output complete.
- Usage received.
- Provider finish reason.
- Provider error.
- Provider request cancelled.

The provider adapter may buffer raw content, but only normalized safe lifecycle information crosses the public SSE boundary.

### 8.2 OpenAI

Use the Responses API streaming interface supported by the selected model.

Normalize relevant lifecycle events such as:

- Response created.
- Output text delta.
- Response completed.
- Error.

Buffer structured SQL output on the backend. Do not send raw incomplete structured output to the UI.

### 8.3 Anthropic

Normalize:

- Message start.
- Content block start.
- Text or JSON deltas.
- Content block stop.
- Message delta.
- Message stop.
- Ping.
- Stream error.

Unknown future event types must be ignored safely and recorded in backend diagnostics.

Do not forward thinking deltas or signatures. Even when a model supports summarized thinking, the primary product trace remains SlayQL's factual stage evidence.

### 8.4 DeepSeek

Normalize data-only SSE chat-completion chunks and the terminal `[DONE]` message.

Request final usage data when the provider supports a streamed usage block.

Do not expose `reasoning_content`. The SlayQL trace is provider-neutral and must remain visually consistent when users switch models.

### 8.5 Provider errors

Map provider-specific failures to stable product codes:

- `invalid_provider_credentials`
- `provider_rate_limited`
- `provider_budget_exhausted`
- `model_unavailable`
- `provider_context_too_large`
- `provider_invalid_output`
- `provider_timeout`
- `provider_overloaded`
- `provider_service_failure`

Never silently switch providers. Preserve the question and offer retry or a confirmed model switch.

## 9. SlayQL trace UX

### 9.1 Default presentation

Use a vertical timeline with:

- Compact stage icon.
- Stage label.
- Pending, active, passed, warning, failed, or cancelled status.
- Duration after completion.
- One concise evidence sentence.
- Expand control when more evidence is available.

Only the active stage should animate. Completed stages remain stable to avoid visual churn.

### 9.2 Stage labels

Use understandable labels:

- Understanding the question.
- Finding relevant data.
- Mapping table relationships.
- Grounding business terms.
- Generating a SQL candidate.
- Validating identifiers and policy.
- Running the query.
- Preparing the answer.
- Selecting a visualization.

Technical details such as RBP, BM25, QOC, and `sqlglot` belong in expanded evidence with tooltips. Do not require enterprise reviewers to understand research terminology.

### 9.3 Timing thresholds

- Under 400 ms: avoid flashing a skeleton.
- After 400 ms: show the active-stage skeleton.
- After 3 seconds in one stage: show elapsed time.
- After 10 seconds in provider generation: show "The selected model is still working" and keep cancel visible.
- Near configured timeout: show the remaining timeout window without fake precision.

### 9.4 Failure placement

Display a failure at the stage that failed. Keep prior passed stages visible. The recovery action appears directly below the failed stage and again in the workspace action bar.

Do not replace the entire workspace with a generic error page.

## 10. Workspace layout

### 10.1 Desktop

Use an unframed three-region workspace:

- Conversation and composer on the left.
- Main answer, table, visualization, and SQL canvas in the center.
- Collapsible SlayQL trace and lineage inspector on the right.

The center must receive most width. Side panels are resizable within fixed minimum and maximum widths.

### 10.2 Tablet

- Conversation remains visible.
- Trace becomes a slide-over panel.
- Results use full available width.
- SQL and charts preserve stable minimum heights.

### 10.3 Mobile

- Use one column.
- Composer remains anchored after the conversation.
- Results tabs are horizontally scrollable without clipping labels.
- Trace opens as a full-height sheet.
- SQL uses horizontal scrolling.
- The result table defaults to a column-focused mobile view.
- Visualization controls open in a bottom sheet.

Do not attempt to display the full desktop split view at mobile width.

## 14. Result profiling

Profile returned columns using database metadata and bounded row inspection.

Semantic types:

- Identifier.
- Category.
- Text.
- Boolean.
- Integer.
- Decimal.
- Currency.
- Percentage.
- Date.
- Datetime.
- Duration.
- Latitude.
- Longitude.
- Unknown.

Profile fields:

- Null count.
- Distinct count.
- Minimum and maximum where meaningful.
- Whether values are positive, negative, or mixed.
- Whether a numeric field is likely an identifier.
- Date interval and ordering.
- Category cardinality.
- Whether result rows were truncated.

Do not infer currency solely from decimal values. Prefer database comments, aliases, semantic catalog metadata, and explicit unit metadata.

## 15. Deterministic chart recommendation

Chart selection must be deterministic and explainable. Do not make a second language-model call merely to choose a chart.

### 15.1 Recommendation rules

| Result shape | Default |
| --- | --- |
| One row and one useful measure | KPI |
| Date/datetime plus one measure | Line |
| Date/datetime plus two compatible measures | Multi-line or composed |
| Category plus one measure | Bar |
| Category plus two to four compatible measures | Grouped bar |
| Category, series, and one measure | Grouped or stacked bar |
| Two continuous numeric measures with at least five rows | Scatter |
| Two to six positive categories representing a verified whole | Donut |
| Ordered buckets plus one measure | Area or bar |
| Mostly text, identifiers, high cardinality, or ambiguous units | Table |
| No rows | Empty result, no chart |

### 15.2 Hard rules

- Default to table when uncertain.
- Never use pie or donut for negative values.
- Never use pie or donut without a defensible part-to-whole relationship.
- Never show more than six pie or donut slices.
- Prefer horizontal bars for long labels.
- Prefer bars over lines for unordered categories.
- Prefer a zero baseline for bars.
- Do not combine incompatible units on one axis.
- Do not hide truncation.
- Do not aggregate already aggregated SQL output again unless the user explicitly chooses it.
- Do not recommend a map in the demo unless valid latitude/longitude or a supported geographic key exists.
- Do not generate a chart from a single identifier column.

### 15.3 Why this chart

Display an optional concise explanation:

"Bar chart selected because the result contains one category and one currency measure across six rows."

This explanation comes from deterministic rules, not model reasoning.

## 16. Supported chart experiences

### 16.1 KPI

- Primary value.
- Optional comparison value and direction.
- Unit-aware formatting.
- Source and time-window subtitle.
- No oversized marketing typography inside compact dashboards.

### 16.2 Bar

- Vertical and horizontal orientation.
- Grouped and stacked variants.
- Sort by category or value.
- Top-N control.
- Long-label handling.
- Optional data labels.

### 16.3 Line and area

- Time-aware x-axis.
- Missing interval behavior documented.
- Multiple series with visible legend.
- Hover crosshair and shared tooltip.
- Optional brush/zoom for more than 30 points.
- No smoothed curve when smoothing could imply nonexistent values.

### 16.4 Scatter

- Numeric x and y.
- Optional category color.
- Tooltip with exact values.
- No trend line unless computed and clearly labeled.

### 16.5 Pie and donut

- Strict suitability rules.
- Direct labels only when they fit.
- Legend plus percentage and absolute value.
- "Other" grouping only when disclosed.

### 16.6 Composed

- Bar and line only when measures have compatible meaning or clearly separated axes.
- Axis units must be visible.
- Dual axes require an explicit warning and are never the automatic default.

## 17. Visualization builder UX

Use a compact inspector, not a long form.

Controls:

- Chart type segmented icon control.
- X/category field menu.
- Measure field menu.
- Series field menu.
- Aggregation menu when permitted.
- Sort menu.
- Top-N numeric stepper.
- Stacked toggle.
- Labels toggle.
- Legend toggle.
- Number-format menu.
- Date-granularity menu.
- Title and subtitle inputs.
- Reset to recommendation.

Behavior:

- Validate every change immediately.
- Keep the last valid chart visible when a new mapping is invalid.
- Explain incompatible field combinations next to the control.
- Provide undo and redo.
- Persist unsaved edits locally for the current session.
- Use stable chart dimensions so controls and loading states do not shift layout.

Natural-language chart edits may be a later enhancement. They are not needed for the first demo unless implemented through the same validated chart specification.

## 18. Chart interaction UX

- Hover or keyboard focus reveals a formatted tooltip.
- Clicking a legend item toggles a series without deleting it.
- Clicking a mark reveals a detail popover with exact dimension and measure values.
- "Ask about this point" creates a follow-up draft containing the selected dimension filter; it must not submit automatically.
- "View rows" switches to the table and applies a local highlight/filter.
- Full-screen view retains title, legend, source, truncation, and export controls.
- Reset view restores zoom, hidden series, and local filters.

Do not silently rewrite or rerun SQL after chart interaction.

## 19. Unique SlayQL visualization features

The module should differentiate SlayQL through trust and provenance rather than decorative novelty.

### 19.1 Field lineage

For every axis and series, show:

- Result column.
- SQL expression or alias.
- Source table and column where available.
- Aggregation.
- Unit.

Selecting a field may highlight the corresponding SQL expression and lineage node.

### 19.2 Validation badges

Show factual badges:

- Complete result or truncated result.
- Aggregated by SQL.
- Locally sorted.
- Top-N applied.
- Synthetic demo data.
- Edited SQL.

Never show an invented confidence percentage.

### 19.3 Model comparison overlay

When two model runs produce equivalent result schemas:

- Allow side-by-side SQL and validation comparison.
- Overlay or juxtapose charts only if returned data is equivalent.
- Explain when comparison is unavailable due to different result shape or values.
- Never imply chart similarity proves SQL correctness.

### 19.4 Trace-to-chart connection

The SlayQL trace should connect:

- User phrase.
- Grounded catalog fields.
- SQL projection and grouping.
- Result columns.
- Visual encodings.

This creates an inspectable path from question to chart without exposing model thoughts.

## 20. Loading, empty, and error states

### 20.1 Loading

- Use stable chart skeleton axes after 400 ms.
- Show rows received for incremental execution.
- Keep chart type controls disabled until profiling is sufficient.
- Do not animate a chart repeatedly for each row batch.

### 20.2 Empty result

Show:

- "The query completed but returned no rows."
- SQL and filters used.
- Modify question and edit SQL actions.
- No empty axes or fake chart.

### 20.3 Unsuitable result

Show the table with:

- "A chart would not improve this result."
- The rule-based reason.
- Manual chart builder access when at least one valid mapping exists.

### 20.4 Truncated result

Display a persistent notice on table and chart. The chart subtitle must state that it reflects the returned row limit.

### 20.5 Visualization error

If rendering fails:

- Keep the table available.
- Show a retry-render action.
- Offer reset to recommended chart.
- Log the chart spec and error without result values.

### 20.6 Stream failure

If the event stream disconnects:

- Preserve messages, trace, SQL, rows, and chart.
- Show "Reconnecting to this run".
- Allow cancellation through a normal POST request.
- Restore from replay or snapshot.
- Never show the run as failed until the backend reports failure or restoration is impossible.

## 21. Accessibility

Visualization requirements:

- Enable the Recharts accessibility layer where supported.
- Provide a textual chart summary.
- Provide an equivalent data table.

- Maintain sufficient contrast.
- Make legend items and marks keyboard reachable where interaction is offered.
- Format tooltip values for screen-reader clarity.
- Do not rely on hover alone.
- Use palettes that remain distinguishable for common color-vision deficiencies.

## 29. UAT scenarios

5. A slow provider shows elapsed time and remains cancellable.
6. SQL does not appear until a complete provider response has been parsed.

14. Cancelling execution stops the database query.
15. Disconnecting the stream preserves content and reconnects without duplicate stages.
16. Refreshing the page restores the run state.
17. A terminal run closes its event stream.
18. A provider failure offers retry and confirmed model switch without silent failover.
19. A category-and-measure result recommends an appropriate bar chart.
20. A time-and-measure result recommends an appropriate line chart.
21. An unsuitable high-cardinality result defaults to table.
22. A misleading pie chart cannot be selected for negative or non-part-to-whole data.
23. "Why this chart" states a factual rule-based explanation.
24. Chart lineage connects visual fields to result columns and SQL expressions.
25. Truncated results remain labelled in the table, chart, and export.
